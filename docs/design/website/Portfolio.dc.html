case study
Java · Spring Boot · personal project · Jun 2026 — present

QuitQOS

A mobile app that helps people quit IQOS and track their recovery journey — a real-time quit timer, science-based health milestones and streak achievements. I designed and built the entire backend in Java and Spring Boot.

Repository status: in development

The problem

Quitting is a long game, and motivation decays fast. The app needed to keep a precise, tamper-resistant quit timer, recognise health milestones at the right moment, and reach the user with a push notification even when the app was closed for days.

What I built

Domain-first REST API

Domain modeling, REST API design and schema evolution across 6 Flyway migrations — every change versioned and repeatable across environments.

Stateless JWT authentication

A custom Spring Security filter chain on top of Firebase Auth, issuing short-lived access tokens with rotating refresh tokens — no server-side session state.

Scheduled milestone engine

A @Scheduled background job detects milestone completions and triggers FCM push notifications, decoupled from any user request.

Tested service layer

39 unit tests with JUnit and Mockito covering business logic across 7 services, so refactors stay cheap.

Django · FastAPI · AWS · personal project · Jan 2026 — present

PaceUp

An AI-powered running coach for iOS. A chatbot builds personalised training plans (Easy / Long / Tempo / Interval) that land on an in-app calendar, with stats chat and pre-workout reminders.

Repository status: live on AWS

The problem

A single workout save has to fan out into stats, achievements, notifications and plan adjustments — without turning the request into a slow, brittle monolith of side effects. Payments had to survive webhooks and clients racing each other.

What I built

Event-driven Django backend

6 apps and 18+ REST endpoints; Django signals let one workout save trigger stats, achievements and notifications independently.

Race-safe subscriptions

RevenueCat integration with idempotent purchase verification across concurrent webhook and client events.

3-service AWS architecture

Django + FastAPI + React Native on ECS Fargate sharing one RDS PostgreSQL instance, behind a shared ALB with host-based routing, ACM wildcard cert and Route 53 aliases for 3 subdomains.

5–10 minute deploys

GitHub Actions pipeline: build, ECR push, ECS rolling deployment — commit to production without manual steps.

Client project · NovaDSA · Dec 2025 — present

Matlı

An enterprise conversational analytics platform: business users ask questions in natural language and get answers from their own data. I built the backend and chatbot service end to end, plus the Next.js frontend.

private client work · no public repo

The problem

An LLM answer is only useful if the conversation around it is durable: multiple users, long threads, and state that survives a reload or a redeploy. The platform also had to run in dev and prod on shared enterprise infrastructure.

What I built

Django REST API + FastAPI AI service

A clean split: Django owns domain and auth, a FastAPI + LangGraph service owns agent orchestration against AWS Bedrock.

Conversation & threading model

Conversations and messages modeled in PostgreSQL to support multi-user chat history with persistent state across sessions.

Multi-environment EKS deployment

Docker images and Kubernetes manifests for all services on an existing EKS cluster, dev and prod side by side under shared networking and routing.

Next.js frontend

Streaming chat interface wired to the API, with conversation history and session restore.
